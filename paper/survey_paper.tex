\begin{abstract}
Small teams and classrooms often want a private chat that stays on their own network, but the usual options are either heavy (federated protocols, brokers, web stacks) or simple demonstrations with no persistence, identity or protection from the network or from whoever runs the server. We present LANChat-H, a LAN chat system whose core uses only the Python standard library. It combines length-prefixed TCP framing with a plain-text fallback for older clients, a bounded outbound queue per client that isolates slow receivers, TLS with trust-on-first-use pinning, memory-hard credentials with lockout and rate limits, server-checked roles, SQLite persistence, ticketed file transfer and a hash-chained audit log. On top, end-to-end encryption (X25519, Ed25519, ChaCha20-Poly1305) covers private messages, files and an optional group room, so the server stores only ciphertext; the room uses one-way key chains per sender and epoch, so late joiners read only what follows and removed members never receive new keys. On one laptop over loopback, median delivery latency stayed between 2.7 and 5.8 ms for up to 100 receivers; when one receiver stopped reading, a sequential-relay baseline stopped delivering to everyone after about 232 messages while LANChat-H delivered all 6000 of 6000; encrypting a message costs about 0.3 ms and a 20 MB file about 31 ms; and a test that scans every frame the server handles, with its database and stored files, finds none of the secrets of encrypted conversations. About 10,600 lines are covered by 452 tests and 370 scripted checks. Limits: no forward secrecy, metadata visible to the server, one machine, no asynchronous baseline.
\end{abstract}

\section{Introduction}\label{sec:intro}
%======================================================================
Small teams, classrooms and labs often want somewhere to talk and share files that stays on their own network. The mainstream answers are heavy: federated protocols such as XMPP, brokers such as MQTT, or web stacks with databases, containers and accounts held by third parties. The lightweight answers are the opposite: a few dozen lines of sockets that broadcast text, with no identity, no history, no protection from anyone on the network and none from whoever runs the server. Between the two there is little that a student, a teacher or a small office can read in an afternoon, start with one command, and still trust with private conversations.

Filling that gap exposes four problems that look separate but interact. First, TCP offers a byte stream, so a chat protocol must define its own message boundaries \cite{rfc9293,stevens}, and that definition has to survive new features and older clients. Second, a server with many long-lived connections must not let one slow or stalled client delay the others, a head-of-line problem that sequential broadcast has by construction. Third, a local network is not a trust boundary: any host can connect, sniff and impersonate, so the system needs transport security, identity, throttling and an audit trail. Fourth, the person who runs the server should not automatically be able to read private conversations, which calls for end-to-end encryption in a system whose server also relays, stores, searches and moderates messages.

This paper presents LANChat-H, a chat system for local networks that addresses all four in one small code base whose core uses only the Python standard library \cite{pysocket,pythreading}. It began as a minimal threaded relay and grew through a sequence of milestones, each leaving earlier behaviour and the terminal client working (Section~\ref{sec:path}). The contributions are:
\begin{enumerate}
  \item a protocol and server design that keeps framing simple and compatible: length-prefixed frames carrying plain text or versioned JSON events, a renderer that lets text-only clients keep working as features are added, and a bounded outbound queue with a writer thread per client that isolates slow receivers;
  \item a layered security design for a trusted-network deployment: TLS with trust-on-first-use pinning, memory-hard credentials with lockout and rate limits, roles checked on the server, ticket-authorised file transfer with hash verification, and a hash-chained audit log;
  \item an end-to-end encryption layer for a server that also stores and relays: private messages and files, and an optional group room built on one-way per-sender key chains per epoch (late joiners read only what follows, removed members never receive the new keys), with key rotation, recovery and an app lock, all from audited primitives;
  \item an implementation of about 10,600 lines with one optional third-party package, covered by 452 automated tests and 370 scripted checks of the real window, including a test that scans every frame the server handles for the secrets of encrypted conversations; and
  \item a measured evaluation on one machine, with the limits of the design and of the measurements stated.
\end{enumerate}
Section~\ref{sec:related} places the work among related systems. Section~\ref{sec:goals} states the goals and the threat model. Section~\ref{sec:design} describes the design, and Section~\ref{sec:impl} the implementation. Section~\ref{sec:eval} evaluates it, Section~\ref{sec:discussion} discusses lessons and limits, and Section~\ref{sec:conclusion} concludes.

\section{Background and Related Work}\label{sec:related}
%======================================================================
\textbf{Transport and framing.} TCP provides a reliable, ordered, full-duplex byte stream and nothing more \cite{rfc9293,rfc793,jacobson,rfc5681,tanenbaum,kurose}: one \code{send()} need not correspond to one \code{recv()}, and functions that only the application can complete, such as message boundaries, cannot be delegated to the lower layer \cite{stevens,saltzer}. Delimiter framing, as in the CRLF lines of IRC \cite{rfc1459}, is readable but needs an escaping rule; XML streams as in XMPP still need an outer mechanism to find where a unit ends \cite{rfc6120}; WebSocket and MQTT carry lengths in binary headers \cite{rfc6455,mqtt5}. TCP keep-alive is optional and off by default \cite{rfc1122}, so noticing an unplugged peer needs application-level heartbeats. LANChat-H uses a four-byte network-order length \cite{pystruct,rfc3629}, which is binary-safe and exact at the price of validating the announced length.

\textbf{Serving many clients.} Thread-per-client gives each connection a sequential control flow that is easy to read and debug; event loops multiplex many connections on few threads but turn each into a state machine \cite{kegel,krohn}; staged designs such as SEDA join event-driven stages with bounded queues \cite{seda}; and the threads-versus-events debate is old and unresolved \cite{ousterhout,vonbehren,lee,flash}. Large systems isolate slow consumers with per-connection queues or non-blocking writes, but teaching-scale servers usually broadcast sequentially, so one stalled receiver delays everyone after it. LANChat-H keeps threads for readability and adds the isolation (Section~\ref{sec:concurrency}); it does not claim that threads are the right choice at scale.

\textbf{Messaging systems and secure messaging.} IRC, XMPP, MQTT and WebSocket each solve interoperability and deployment problems (federation, brokers, browsers) that a single-server LAN chat does not have \cite{rfc1459,rfc2812,rfc6120,rfc6121,mqtt5,rfc6455}; Table~\ref{tab:comparison} compares them with LANChat-H. TLS protects the channel \cite{rfc8446}, but the server still sees plaintext. End-to-end designs show how to hide content from a relaying server: the Double Ratchet \cite{signal,cohngordon}, X3DH for asynchronous contact set-up \cite{x3dh}, and Messaging Layer Security for efficient groups \cite{rfc9420}, built on X25519, Ed25519, HKDF and ChaCha20-Poly1305 \cite{rfc7748,rfc8032,rfc5869,rfc8439}; Unger \emph{et al.} compare the designs \cite{unger}. LANChat-H reuses the primitives and the sealed-key and sender-key ideas, not these full protocols.

\textbf{Accounts, trust, audit, discovery and transfer.} Authentication guidance recommends salted memory-hard hashing, checks against common passwords and throttling of repeated failures \cite{nist63b,rfc7914}. SSH's trust-on-first-use host-key model is the precedent for self-signed certificates \cite{rfc4251}. Hash-chained logs make alteration detectable, with a separate commitment needed to detect truncation \cite{schneier99,crosby09}. LAN services are normally found with IP multicast \cite{rfc1112} and multicast DNS \cite{rfc6762,rfc6763}, while small programs use a UDP broadcast, and FTP separated control and data connections \cite{rfc959}, the pattern LANChat-H uses so that a large transfer never blocks the chat. Publish--subscribe and reliable group communication offer delivery guarantees far beyond what a single-server chat provides \cite{eugster,birman87,birman93}.

\section{Design Goals and Threat Model}\label{sec:goals}
%======================================================================
\textbf{Goals.} We set seven goals, each tied to something the evaluation checks.
\begin{enumerate}
  \item[G1] \emph{Small and runnable.} Standard library for the core, one folder, one command, modules small enough to read.
  \item[G2] \emph{Compatible growth.} New features must not break clients that predate them.
  \item[G3] \emph{Isolation.} One slow, stalled or hostile client must not delay or crash the others.
  \item[G4] \emph{Safe on a hostile network.} Encryption in transit, a way to recognise the server, real accounts, throttling, and no file or name that can harm a recipient or the host.
  \item[G5] \emph{Private from the host where it matters.} Private conversations, their files and (optionally) the group room must be unreadable to the server, with keys that survive a lost computer.
  \item[G6] \emph{Accountable and operable.} Roles, an audit trail that shows tampering, administration tools, backups and upgrades that keep data.
  \item[G7] \emph{Verifiable.} Every claim above is backed by a test or a measurement that can be rerun.
\end{enumerate}

\textbf{Threat model.} Table~\ref{tab:threat} lists whom we defend against. We assume the clients' computers are not compromised and that the person comparing security codes is who they say they are. We do not try to hide metadata, to defend a compromised endpoint, or to scale beyond tens of people.

\subsection{Framing, Protocol Versions and Compatibility}\label{sec:framing}
Every message in both directions is a four-byte big-endian length followed by UTF-8 text, as in Listing~\ref{lst:frame}; zero-length and over-long frames close the connection. Two protocol versions share this framing. Version~1 carries plain text lines and is what the terminal client speaks. Version~2 carries one JSON object per frame with a type field (message, edit, delete, reaction, typing, presence, read marker, pin, search, history page, upload, download, key and room events, and so on); a version-2 client announces itself with a JSON hello in the username step, and the server detects the version from the first character. For version-1 clients the server renders every event as the line they have always seen, and sends nothing for events a terminal cannot show, so features were added without breaking the older client (G2). Message text is limited to 3400 bytes so that the JSON envelope always fits one frame; encrypted private messages are limited to 1500 bytes of text, so that the sealed keys and signature still fit in one frame.

MAX_MESSAGE_BYTES = 4096

def send_message(conn, message):
    payload = message.encode("utf-8")
    if len(payload) > MAX_MESSAGE_BYTES:
        raise ValueError("message is too large")
    conn.sendall(struct.pack("!I", len(payload)) + payload)

def receive_message(conn):
    header = _receive_exactly(conn, 4)
    if header is None:
        return None            # peer closed
    (length,) = struct.unpack("!I", header)
    if length == 0 or length > MAX_MESSAGE_BYTES:
        raise ValueError("invalid message length")
    payload = _receive_exactly(conn, length)
    if payload is None:
        return None
    return payload.decode("utf-8")
\end{lstlisting}

\subsection{Concurrency and Delivery}\label{sec:concurrency}
Each connection has a handler thread that reads requests and a writer thread that is the only code writing to that socket. Delivering a message means placing it on every recipient's bounded outbound queue (default 100 entries) without waiting. If a queue fills, the client is not keeping up and is disconnected; it can reconnect and replay history from the database (G3). The welcome and history are written directly before the writer thread starts, so they arrive first and in order. Clients send a ping every ten seconds and the server drops a connection silent for thirty. A user name may be signed in once; a saved sign-in may take over a stale connection. Section~\ref{sec:eval} measures the effect of the queues.

\subsection{Persistence and Features}
Messages, users, reactions, pins, read markers, sessions, public keys and the audit log live in SQLite, so history survives restarts; seven numbered migrations let an older database upgrade in place (G6). A joining client receives the last 50 messages and can page back 50 at a time. Search uses an FTS5 index and falls back to \code{LIKE} where FTS5 is absent. The window supports replies, reactions, edit and delete (deletion keeps a tombstone so quoted replies still resolve), typing indicators, presence, read receipts, mentions, pins and an administrator console. These features stress the protocol: history paging and search need replies that respect back-pressure, edits and deletes need ids that survive reconnection, and, as Section~\ref{sec:e2ee} shows, search, pins and mentions need rethinking when the server cannot read the text.

\subsection{Bulk Transfer}
Pictures, documents and audio do not travel on the chat connection. The client sends an upload request with the name, size and SHA-256; the server checks role, type, size, quota and conversation and replies with a one-time ticket. The client opens a second TLS connection, presents the ticket, and streams raw bytes; the server writes them to a temporary file while hashing, enforces the declared size and a deadline, compares the digest, and only then moves the file into place under its hash and posts the message. Downloads mirror this and are verified by the receiver; a damaged file is never delivered, and a half-finished upload leaves nothing behind. Identical content is stored once, and a file is removed when the last message referring to it is deleted. File names are reduced to a safe base name and executable types are blocked (G4).

\subsection{End-to-End Encryption}\label{sec:e2ee}
End-to-end encryption is the part of the design that changes what the server is. Without it the server decrypts TLS, stores and relays plaintext and can search it; with it the server stores ciphertext and public keys, and everything that needs the words moves to the client.

\textbf{Identities and trust.} Each person has an X25519 key pair for key agreement and an Ed25519 pair for signing, bound by a self-signature \cite{rfc7748,rfc8032}. Secret keys are wrapped on disk with ChaCha20-Poly1305 \cite{rfc8439} under a key derived by scrypt from a passphrase. A 24-character recovery code (about 119 bits) wraps a second copy that the server stores as an opaque backup; because the code is high entropy the server cannot usefully guess it, and a test confirms that neither the keys nor the code appear in the database file. The server keeps only public keys and cannot be trusted to report them honestly, so clients verify each bundle's signature, pin the first key seen for each contact, block sending when it changes until the person has accepted the new one, and offer a sixty-digit safety number computed from both identities for comparison in person or on a trusted call.

\textbf{Private messages.} The sender encrypts the text once under a random key with ChaCha20-Poly1305, seals that key separately for the recipient and for themselves (ephemeral and static X25519 through HKDF-SHA256 \cite{rfc5869}), and signs the whole message with Ed25519, binding the sender and recipients into the associated data. The server checks only the shape and the two names, stores an empty body and the envelope, and relays it. Tampering, a wrong recipient or a forged sender fails to open, and the window flags a reused random message id as a possible replay. Encrypting for the sender as well as the recipient costs a few hundred bytes and lets people read their own history after a restart.

\textbf{Files.} Files are encrypted on the sender's computer in 64 KiB chunks under a random key; each nonce carries the chunk number and a last-chunk flag, so dropped, reordered or added chunks fail. The key, the real name and the type travel inside the encrypted message, so the server stores unreadable bytes under an opaque name and can apply only size and space limits; the receiving window, which alone knows the name, warns before opening a program-like file.

\textbf{The group room.} A sealed copy for every member does not scale to a room, so the room uses sender keys in the style of group messengers \cite{rfc9420}. Each member holds a random chain key per \emph{epoch}, derives the key for message $n$ by $n$ one-way steps, and gives every other member a sealed copy of the chain as it stands, so a member who joins later reads only what follows. The server stores the sealed copies (so they can be fetched again after a restart), enforces the current epoch and strictly increasing message numbers per sender, and starts a new epoch whenever someone is removed or an administrator asks; the removed person never receives the new chain. Mentions are named by the sender because the server cannot read the text, and \code{@everyone} stays administrator-only; pins, quoted replies and search use what the window has decrypted. An administrator switches the room on, after seeing which members have no keys, because people without keys and terminal clients can then neither read nor write.

\textbf{Key lifecycle.} Keys can be rotated (a new identity, with the old ones kept so earlier messages still open and the server keeping the envelopes sealed to them), restored from the recovery code on a new computer with every identity, or reset, which discards history. An idle window locks itself, covering the interface, hiding dialogs and forgetting the keys until the passphrase is entered.

\textbf{What the server still learns.} The server sees who talks to whom, when, the sizes of messages and files, reactions, who is mentioned, each person's role and the membership of the room; it can also withhold or delete messages, though it cannot read or forge them. Section~\ref{sec:discussion} lists the resulting limits.

\section{Evaluation}\label{sec:eval}
%======================================================================
All measurements were taken on one machine: an Apple-silicon laptop (arm64) running macOS 27.0.1 with CPython 3.13.9, with the server and clients on the loopback interface. The source code, tests and scripts (\code{bench/}) are published \cite{lanchatrepo}, and the numbers below are what they printed. Because client and server share one machine, the results show the cost of the software, not of a real network; they are not claims about Wi-Fi or Ethernet performance.

\subsection{Correctness and Security Tests}
The repository holds 22 test modules that run 452 tests, each starting real servers on free local ports. They cover framing (round trip, closed connection, oversized and zero-length frames), the version-1 and version-2 protocols, the database and its migrations, search and paging, TLS and certificate pinning including a changed certificate, discovery, file transfer (round trips, hash mismatch, cut-off uploads, hostile names, expired and reused tickets, quota, concurrent uploads), lockout, rate limits, password rules, saved sign-ins, administrator actions, tamper detection in the audit chain, and the encryption code, which is checked against published test vectors for X25519 and Ed25519 \cite{rfc7748,rfc8032} and then against tampering, wrong recipients, forged senders, replays, damaged and reordered files, and the room's rules for late joiners, removal and message numbering. One test wraps the server's send and receive functions, records every frame the server handles, and scans those frames, the database file and the stored files for the secret text, file names, file contents and file keys of encrypted messages; a companion check shows that the same capture would reveal a plaintext message. A further eleven scripts drive the real window and the terminal client through 370 checks, including runs with every security default on. All of them pass.

\subsection{Fan-Out Latency}
One sender sent 100 messages of about 100 bytes at ten per second to $N$ receivers, each a real client with its own connection; every message was also written to the SQLite database before delivery. Receivers ran in separate processes of at most 20, and latency is the arrival time minus the send time on the machine's monotonic clock. Median latency stayed between 2.7 and 5.8 ms and the 95th percentile below 9.5 ms without TLS; with TLS the figures for 25 and 100 receivers were 4.7 and 6.4 ms (median) and 7.5 and 11.3 ms (95th percentile).

\subsection{Head-of-Line Blocking}
The fan-out cost model predicts the effect of a stalled receiver. With sequential sends, recipient $k$ receives the message after
\begin{equation}
D_k = \sum_{j=1}^{k} s_j , \qquad T_{\text{bcast}} = D_N ,
\end{equation}
where $s_j$ is the time the blocking send to recipient $j$ takes, and if recipient $m$ stalls for an extra time $W$ then
\begin{equation}
D_k \;\ge\; W + \sum_{j=1}^{k} s_j \qquad \text{for all } k \ge m .
\end{equation}
With a bounded queue and writer thread the send to each recipient reduces to an enqueue with cost $q_j \ll W$, so $D_k$ no longer depends on $W$ for $k \neq m$.

To test this we compared LANChat-H with a minimal sequential relay written for the experiment: a thread per client that sends each incoming message to every other client in turn with a blocking \code{sendall}. Both use the same framing. Ten receivers read normally; one more connects first, shrinks its receive buffer to 4 KiB and never reads. A sender sends 600 messages of 2000 bytes at 50 per second. Table~\ref{tab:hol} gives the range over four runs. Once the kernel buffers for the stalled connection were full, after 232 messages (about 460 kB), the sequential relay stopped delivering to every receiver: exactly 2320 deliveries (232 messages to each of ten receivers) arrived in every run, out of 5370 to 5400 expected, and the sender's own sends began to time out after 537 to 540 messages. With the stalled receiver present LANChat-H delivered 6000 of 6000 messages to the ten healthy receivers, and dropped the stalled connection once its queue filled.

\subsection{Confidentiality Check}
The confidentiality claim of G5 is checked by observation rather than by argument. The test wraps the server's receive and send functions so that every frame it handles is recorded. It then has two people exchange a private message, a private edit, a room message and an encrypted file with a caption, and scans all recorded frames, the SQLite file and the stored files for the secret message texts, the real file name and type, the file contents, the file key and the people's secret keys. None appears; the traffic does contain the encrypted envelopes, so the capture is real. A companion check sends a plaintext message through the same capture and finds it, so the scan would notice a leak. Separate tests assert that the database holds an empty body and an opaque attachment name for encrypted messages, that neither a chain key nor a recovery code is stored, and that a removed member, a late joiner and a person without keys cannot open what they should not.

\subsection{Threats to Validity}
The experiments use one machine, one Python version and the loopback interface, so queueing in the network, wireless loss and operating-system differences are absent. Latency includes scheduling of separate Python processes and is not a pure network figure. The synthetic load is regular (fixed rate and size), not a trace of real conversations. The sequential relay is a minimal baseline written for the comparison, not a measurement of any other published system, and the claim that thread-per-client stops being adequate at some size has not been tested because no asynchronous variant was built. The tests show that behaviours occur; they do not prove their absence elsewhere.

\section{Discussion and Limitations}\label{sec:discussion}
%======================================================================
\textbf{Lessons.} A renderer that turns every event into the line an older client expects made incremental growth cheap: twelve milestones later the terminal client still works, for plain conversations. LANChat-H's per-message work (persistence, checks, rendering and the queues) costs a few milliseconds more than a bare relay in our measurements, but the queues remove an entire class of failure, and writing the slow-receiver experiment forced us to say precisely what ``isolation'' means. Testing against real servers and the real window found problems that unit tests of pieces would not: malformed key data that raised an unexpected exception in the key-handling code, a recovery-code ``Done'' button that was packed behind a sibling widget and so invisible, and an ordering bug in which a test thread waited on the server while the window loop it depended on was not running. Finally, end-to-end encryption is less about the cipher than about everything the server used to do with plaintext: search, pins, mentions, quoting, policy checks and moderation each needed a client-side or metadata-based replacement.

\textbf{No forward secrecy.} Private messages use an ephemeral key per message, which protects the sender's side, but theft of a recipient's long-term key would expose earlier messages to anyone holding the ciphertext, and the room's sealed chain copies stay on the server so that history can be re-read. A ratchet \cite{signal,cohngordon} would be the upgrade, at the cost of storing per-device state.

\textbf{Identity is as strong as the comparison.} Keys are pinned on first sight and a change blocks sending, but until two people compare security codes a hostile server could have substituted a key at the very first contact. The same holds for the server certificate under trust on first use.

\textbf{Metadata and moderation.} The server learns who talks to whom and when, sizes and mentions. It cannot read encrypted content, so administrators cannot moderate by reading; they can delete by id, remove people and re-key.

\textbf{Scope of encryption.} Terminal clients and members without keys cannot take part in encrypted conversations; search of encrypted messages covers what the window has loaded; and files shared in readable conversations are stored unencrypted. The window is not a vault: decrypted text lives in memory while it is open.

\textbf{Scale and evidence.} The design is one server, one thread per client and one SQLite connection behind a lock. We do not establish where this stops being adequate; an \code{asyncio} server \cite{pyasyncio} under identical workloads, a multi-host study with packet loss and wireless links, and measurements with more clients are the obvious next experiments. The security claims rest on tests of this implementation, not on a formal analysis or an external review, and the primitives are audited but their composition here is new.

\textbf{Future work.} A ratchet for forward secrecy, multiple devices per person, sealed-sender style protection of metadata, an asynchronous server variant, and an independent security review.

%======================================================================
\section{Conclusion}\label{sec:conclusion}
%======================================================================
LANChat-H shows that a chat system for a local network can combine a simple compatible protocol, isolation of slow clients, layered transport and account security, and end-to-end encryption for private conversations and an optional group room, in a code base small enough to read and with one optional dependency. The measurements on one machine show what the design costs and buys: a few milliseconds of extra per-message work (storage, checks and queueing) in return for a room that survives a stalled receiver, and a fraction of a millisecond per encrypted message in return for a server that holds only ciphertext. A test that scans everything the server handles confirms that claim for the conversations tested. The limits are stated plainly: there is no forward secrecy, the server still sees metadata, no asynchronous variant was compared, and all measurements come from one machine. The next steps are a ratchet, a multi-host evaluation, and an independent review.
